GlossaryWords you will see
  • Entity: a thing the system stores, such as Offer or Deal. One table each.
  • Enumeration: a fixed list of allowed values, such as Available, Reserved, Sold.
  • Command: a request to change something. Query: a request to read something.
  • DTO: the shape of data sent over the API. Entities are never sent directly.
  • Controller: the API entry point that receives a command or query and returns a DTO.
  • Layer: Domain (rules), Application (use cases), Infrastructure (database, email, files), API (controllers).
  • Escrow: money the platform holds until the buyer accepts the delivery.
2 rolesRoles

  • Admin: verifies users, monitors deals, mediates disputes and generates compliance reports.

RulePrices and units
  • Every offer has a quantity, one unit (Kg, Ton, Liter, CubicMeter or Piece) and an asking price per one unit, in EGP. Example: 500 Ton at 1,200 EGP per Ton.
  • A request has a quantity and a unit but no price.
  • The asking price is a starting point. Buyer and seller discuss it in the chat.
  • The buyer proposes a deal with an agreed unit price, prefilled from the asking price. When the seller accepts, quantity and unit price are locked, even if the seller edits the offer later.
  • Deal total = quantity × agreed unit price. The escrow holds the total.
RuleUnits in search and matching
  • Quantities are compared after converting within the same kind: Kg and Ton are mass, Liter and CubicMeter are volume, Piece is a count.
  • Different kinds never match. A request in Liters cannot match an offer in Kg.
RuleTransport
  • The deal shows a distance-based transport estimate.
  • It is not part of the price and not held in escrow, because the platform does not handle logistics yet.
  • When logistics is added, it becomes an extra line on the deal.
RuleChat
  • Every conversation is about one listing: an offer or a request.
  • Any factory can open a conversation on another factory’s listing, never on its own.
  • One conversation per listing and per interested factory. There are no free-form direct messages.
RuleAudit log
  • Written from the first release by one central mechanism, not by hand in each handler.
  • Covers every create, update, delete and status change by users and admins, plus sign-ins and password changes.
  • Not logged: reads, and chat message text (messages have their own table).
  • Append-only. The actor is empty only for system jobs and failed sign-ins. Details never contain passwords or tokens.
RuleIdentity
  • One User account per factory. Business actions (offers, requests, deals, chat) belong to the factory profile; account data and notifications belong to the user.
  • Buyer and Seller are roles inside a single deal, not account types.

How it worksAdmin dashboard
  • It is not a separate system. It is the same app and API, with screens and endpoints that only the Admin role can open.
  • The frontend hides the admin routes for other roles. The backend refuses them with a 403, which is the check that counts.
  • Its numbers are counts over tables that already exist (users, offers, deals, disputes, impact records), so it needs no table of its own.
How it worksUser settings
  • One UserSettings row per account, created with defaults at registration.
  • The notification service reads it before it pushes or emails an alert.
  • Changing a password checks the current one first, then stores a new hash.
  • Factory details stay under Profiles, not Settings.
How it worksPlatform settings
  • Key and value rows an admin can edit, such as the inspection period in days or the transport cost per kilometre.
  • Services read them (cached) instead of hard-coding numbers, so changing one needs no new release.
  • Each material category carries a CO2 factor, which is how a completed deal turns into an impact record.
How it worksAudit log
  • Every create, update, delete and status change by a user or an admin writes a row automatically, from the first release.
  • The row is saved in the same database transaction as the change, so neither can exist without the other.
  • The screen to browse it can come later. The writing cannot.
MVPWhat the MVP skips
  • Seed the admin account and the material categories directly in the database.
  • The audit log is not skipped. It is written from day one.
  • Build the admin screens after the user flow works.
